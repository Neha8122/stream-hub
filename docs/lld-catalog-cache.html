Catalog Cache LLD

The catalog is read thousands of times a second and changes rarely, so reads come from Redis. The interesting part is what happens the moment a popular entry expires: without care, every request at that instant goes to Postgres at once.

2 · The read path

Each cached entry holds

valuethe title as JSON
freshUntilnow + 5 min ± random jitter
Redis TTL1 hour: the stale copy stays available well past freshUntil

The jitter spreads expiries out, so keys cached together don't all go stale in the same second.

get(titleId)

  1. Fresh hit: return it. Most requests end here.
  2. Stale hit: try SET lock NX EX 5. Winner reloads from Postgres and rewrites the entry. Everyone else returns the stale value immediately.
  3. Complete miss: the lock winner loads; the others wait for the entry to appear for as long as someone holds the lock. If the lock is free and there's still no entry, the loader failed, and the next request takes the lock and loads.
  4. Double-check: whoever wins the lock looks at the entry once more first. Another request may have refreshed it and released the lock a moment ago.
  5. Not found: cache a short-lived "missing" marker too, so a stream of requests for an id that doesn't exist can't hammer the database.
  6. Redis down: read Postgres directly (slower, still correct), and count it on a metric.

3 · Writes and what proves it

Writes

Update Postgres first, then delete the cache key (don't rewrite it): the next read loads the new value. Deleting avoids a race where two concurrent writers leave the cache holding the older of the two values. The change is also published for the search indexer (step 2).
