stream-hub · high-level design

Stream Hub HLD

The backend of a video streaming service: browse a catalog, search it, press play, pick up where you left off, and get recommendations that react to what you just watched. Built as microservices around a Kafka event stream, with caching, resilience and observability throughout, plus AI search and an assistant that keeps working when the AI doesn't.

System view

Flow 1 · Opening the home page

  1. Gateway checks the token and the user's rate limit, routes to the recommendation service.
  2. Recs reads the user's live features from Redis (what they watched in the last hour).
  3. Finds candidates by vector similarity in Elasticsearch, re-ranks them with the features.
  4. Continue-watching and catalog rows come from Redis cache; a miss reads Postgres once, then caches.
  5. Over the latency budget? Serve "popular in your region" instead: degrade, don't fail.

Flow 2 · Pressing play

  1. Playback opens a session in Redis and returns the stream URL.
  2. Every 30 s the player sends a heartbeat (position); playback keeps it in Redis.
  3. Playback publishes playback-events to Kafka, keyed by userId so one user's events stay in order.
  4. History consumer updates continue-watching; feature consumer updates live features.
  5. The next home page already reflects what was just watched: seconds, not a nightly batch.

Peak concurrent viewers1M of 10M usersstateless services, scale out behind the gateway
Heartbeats1M ÷ 30 s → ~33k/s, ~200 B each (~7 MB/s)never write each one to Postgres: keep position in Redis, persist on stop or every few minutes (~2k writes/s)

The project runs a scaled-down version on one machine (Docker Compose, then kind for Kubernetes) and reports measured numbers from that setup, not these.

Deep dives to be ready for

QuestionAnswer in this design
A consumer crashes after writing but before committing its Kafka offset. What happens?Kafka redelivers. Consumers are idempotent: every event has an id, and the write plus a processed_events row happen in one DB transaction, so a redelivered event changes nothing.
One bad message keeps failing.Retry with backoff a few times, then move it to a dead-letter topic so the partition isn't stuck behind it.
33k heartbeats a second into Postgres?No: write-behind. Latest position in Redis; persist on stop, on a timer, or when it changes by a lot.
A hot title expires from cache and 10k requests miss at once.Stampede protection: one request rebuilds while the others get the stale value; TTLs get random jitter so keys don't expire together.
The recommendation store is slow.Timeout plus bulkhead so it can't drain the threads, then a fallback row. The page still loads.
The LLM is down or takes 10 s.Circuit breaker opens, the assistant answers from search instead, and the dashboard shows a fallback rate. The model may only return titles that exist in the catalog.
How do you know it's healthy?SLOs (e.g. 99.9% of home loads under 300 ms), burn-rate alerts, and a trace for any slow request across every service.
